# Just Do It — 全自動任務執行

不問、不等、不停。收到任務描述後自動完成所有事情。

**完整流程：**
```
Phase 1: Spec 生成（自動，無需確認）
Phase 2: Chunk 並行執行（subagents 分工）
Phase 3: Code Review + 測試驗收
Phase 4: 最終報告
```

---

## `--tdd` 模式（選用）

參數含 `--tdd` 時啟用。沒有帶參數就是一般模式，以下全部不適用。

**核心規則：先寫測試、親眼看它失敗（紅燈），再寫實作讓它通過（綠燈）。** 沒看過紅燈的測試，無法證明它真的抓得到問題。

**不詢問**：`--tdd` 本身就是使用者的選擇，照樣全自動，不再問「要不要寫測試」。

### 啟動檢查（Phase 1 最前面）

用 Phase 3-2 的技術棧表偵測測試框架：

- **有框架** → 啟用 TDD，往下走
- **沒有框架** → **不自行安裝或初始化測試框架**（會新增設定檔、超出任務範圍），整個任務改回一般模式執行，並在最終報告「未執行／無法驗收」區寫明：「`--tdd`：專案無測試框架，已改用一般模式」

### Spec 增加的內容（Phase 1）

每個 chunk 在「驗收條件」後加一節：

```markdown
**測試案例**（--tdd）：
- 測試檔：`path/to/XxxTest.java`（列入本 chunk 的檔案清單，參與檔案互斥檢查）
- 案例：`test_空email應被拒絕` — 對應驗收條件 1
- 預期紅燈原因：尚未實作 email 檢查，斷言失敗
```

- 每條驗收條件至少對應一個測試案例
- 無法自動測試的 chunk（純樣式、設定檔、文件、需要真實外部服務）標 **`TDD 豁免：<原因>`**，照一般模式執行，不可為了湊數寫空洞測試

### 執行順序（Phase 2，每個非豁免 chunk）

1. **紅燈**：先只寫測試，執行，確認**失敗**，且失敗原因是「功能還沒做」（斷言失敗、呼叫尚未實作的方法）。如果是測試本身寫錯（語法錯、import 錯、環境錯），先修測試再跑，直到失敗原因正確。**測試一開始就通過** → 代表它沒測到新行為，改寫測試
2. **綠燈**：寫最少的實作讓測試通過。**不可修改測試斷言來讓它通過**（測試本身有 bug 除外，須在回報中說明）
3. **回歸**：跑與本 chunk 相關的測試（範圍見 2-2「測試範圍」），完整測試由主線在 Phase 3 統一跑
4. **回報**：在 chunk 回報檔附上紅燈與綠燈的執行指令與輸出結尾（各約 10 行）

## Phase 1：Spec 偵測 + 生成

### 1-1 偵測是否已有 Spec

**依序執行以下偵測，任一命中即停止：**

**偵測 A — 對話 context**
回顧當前對話，判斷使用者是否已提供明確的任務內容，符合以下任一條件即視為「已有 spec」：
- 對話中出現了明確的任務清單（例如：剛列出的 TODO 項目、OPT-XXX 清單）
- 對話中有 spec 文件的完整或部分內容
- 使用者說「做 XXX 幾項」、「完成上面這些」、「照剛才列的去做」

**偵測 B — 檔案系統**
用 Glob 掃描當前目錄，查找 spec 類檔案（優先序由上到下）：
- `just-do-it-spec.md`
- `*SPEC*.md`、`*spec*.md`（如 `OPT-SPEC.md`）
- `TODO.md`、`todo.md`
- `implementation_plan.md`
- `*plan*.md`、`*PLAN*.md`

**「完整 Spec」的判準**：檔案必須含有 Chunk（或等價的任務切分）＋驗收條件結構，才能走路徑 A。`TODO.md` 這類功能總覽／待辦清單**一律最多算「任務清單」（路徑 B）**，不可直接當完整 Spec 執行（實測踩坑：1800 行的功能總覽 TODO.md 會被誤判）。

### 1-2 根據偵測結果決定路徑

**關鍵區分：任務清單 ≠ Spec**

| 類型 | 特徵 | 處理方式 |
|------|------|---------|
| **完整 Spec** | 有具體檔案路徑 + 驗收條件 + 實作細節 | 直接跳 Phase 2 |
| **任務清單** | 只有項目名稱/描述，無檔案路徑 | 快速 Phase 1（以清單為起點補全） |
| **什麼都沒有** | 只有模糊的需求描述 | 完整 Phase 1（從頭分析） |

```
路徑 A — 完整 Spec（跳過生成）
├── 偵測到：有明確檔案路徑 + 驗收條件的 spec 文件（檔案或對話中）
├── 使用者有指定範圍 → 篩出對應 chunks
├── 未指定範圍 → 全部執行，不限數量
└── 顯示：
    📋 偵測到完整 Spec：[來源]
       本次執行：[項目清單]，共 {N} 個 chunks
       直接進入執行...

路徑 B — 任務清單（快速 Phase 1）
├── 偵測到：對話或檔案中有任務清單，但只有名稱/描述，無實作細節
├── 以清單為起點，針對每個任務：
│   - 用 Grep/Glob 定位相關檔案和程式碼位置
│   - 根據程式碼現況擬定驗收條件
│   - 產出完整 just-do-it-spec.md
├── 使用者有指定範圍 → 只對選定項目做上述分析
└── 顯示：
    📋 偵測到任務清單：[來源]，共 {N} 項
       進行快速 Spec 分析（補全檔案路徑與驗收條件）...
       [分析完成後]
    📄 Spec 已產出：just-do-it-spec.md，共 {N} 個 chunks
       開始執行...

路徑 C — 無 Spec（完整 Phase 1）
└── 走 1-3 從頭分析
```

### 1-3 重新生成 Spec（僅在未偵測到 spec 時執行）

**覆寫保護**：若當前目錄已有 `just-do-it-spec.md`，先將舊檔歸檔到 `docs/specs/just-do-it-spec-{YYYY-MM-DD}-{舊任務slug}.md`（目錄不存在就建立），再寫新檔。上一輪的規格是歷史紀錄，不可無聲覆寫。

讀取專案上下文：
1. 偵測技術棧（依序讀取：`package.json` / `pom.xml` / `build.gradle` / `pyproject.toml` / `requirements.txt` / `*.csproj` / `CLAUDE.md`）
2. 用 Glob 掃描專案結構（忽略 `node_modules/`、`.git/`、`dist/`、`build/`、`target/`）
3. 用 Grep 搜尋與任務描述相關的現有程式碼

將以下內容寫入 `just-do-it-spec.md`（放在當前目錄）：

```markdown
# [任務名稱] — Just Do It Spec

## 目標
（一句話描述要達成什麼）

## 背景
（為什麼需要做這個，現有功能現況）

## 技術範圍
- 技術棧：
- 主要影響模組/檔案：

## 介面契約（鎖定，不可偏離）

（自產 spec 也必須有這一節——並行拆 chunk 的場景正是最需要契約的場景。
把並行 chunk 之間共用的類別名／方法簽名／DTO 欄位／API 路徑／key 規則先在此釘死，
否則多個 agent 會各自發明命名，事後才在 review 撞出來。
格式：| 類型 | 識別名 | 定義 |，類型：ENTITY_CLASS / SERVICE_INTERFACE / METHOD_SIGNATURE /
DTO_CLASS / API_ENDPOINT / FUNCTION_SIGNATURE / DATA_MODEL。
若任務確實沒有任何跨 chunk 共用介面，寫「無跨 chunk 介面」並說明原因。）

## Task Chunks

### Chunk 1: [名稱]
**目的**：
**需要新增/修改的檔案**：
- `path/to/file` — 說明要做什麼

**驗收條件**：
- [ ] 條件 1
- [ ] 條件 2

**相依**：無（可並行）/ Chunk N 完成後才開始

---

### Chunk 2: [名稱]
（同上格式）

---

## 整合驗收條件
- [ ] 所有 chunk 完成後的整體驗收項目
- [ ] 測試通過
- [ ] 不破壞現有功能
```

### 1-4 Chunk 設計原則

- **單一職責**：每個 chunk 只做一件清楚定義的事（DB schema / API 實作 / 前端元件 / 測試）
- **檔案互斥（硬規則）**：同一批次並行的 chunks，檔案清單必須互斥。兩個 chunk 要動同一個檔案 → 合併成一個 chunk，或拆到不同批次（Edit 工具要求檔案未被改動，並行寫同一檔第二個 agent 會直接失敗）
- **每個 chunk 必須明列完整檔案清單**：這是批次排程做互斥檢查的依據，不可省略
- **最小化相依**：盡量讓 chunks 可以並行執行
- **有相依性的 chunks** 標記清楚，分批執行
- **chunk 數量**：不限上限。太小（只有 1 步驟、改 1 個檔案）直接做不用拆；多項任務照單全收，由使用者自行判斷複雜度
- **每個 chunk 必須包含明確的驗收條件**，方便後續 Review

產出 spec 後顯示：
```
📄 Spec 已產出：just-do-it-spec.md
   共 {N} 個 chunks，{X} 批並行執行
   開始執行...
```

## Phase 2：並行執行

### 2-1 分析相依順序，排定批次

分析 spec 中各 chunk 的相依關係，分成多個「執行批次」：

- 無相依的 chunks → 同一批次，並行執行
- 有相依的 chunks → 等前置批次完成後才執行
- **排批前做檔案互斥檢查**：同一批次各 chunk 的檔案清單有交集 → 重排（合併 chunk 或錯開批次），不可讓兩個 agent 並行編輯同一檔案

範例：
```
批次 1（並行）：Chunk 1（DB Schema）、Chunk 2（資料模型）
批次 2（並行）：Chunk 3（API 實作）、Chunk 4（前端元件）— 相依批次 1
批次 3（循序）：Chunk 5（整合測試）— 相依批次 2
```

### 2-2 Spawn Subagents

**每個 chunk 各 spawn 一個 `general-purpose` subagent**，同一批次的 agents 同時送出（並行）。

每個 subagent 的 prompt 結構：

```
你是一個實作 agent，負責完成以下任務 chunk。請先用 Read 工具讀 `{spec 檔案的絕對路徑}` 取得完整 spec（含介面契約），然後直接執行，不需要確認。

═══════════════════════════════════════
你負責的 Chunk：
[貼入對應 chunk 的完整規格]

═══════════════════════════════════════
執行要求：
1. 按照「驗收條件」逐一完成，每條完成後在心中打勾
2. 只修改此 chunk 規格中列出的檔案範圍
3. 嚴格遵守 spec 的「介面契約」區塊，不可自行發明命名
4. 若發現需要動到 chunk 範圍外的檔案，先做必要的最小修改，並在回報中說明原因
5. 測試範圍：只跑與本 chunk 相關的測試——自己新增或修改的測試檔、改動模組對應的測試資料夾（專案 CLAUDE.md 有「測試對照」時依它）。不要跑完整測試，完整測試由主線在 Phase 3 統一跑一次。例外：改到被很多地方 import 的共用核心檔、或改了測試共用設定（conftest、fixtures）時，可以跑完整測試並在回報說明原因。
6. 完成後用 Write 工具把回報寫入 `.just-do-it/chunk-{N}-report.md`（`{N}` 用該 chunk 在 spec 裡的編號，數字或字母皆可，與 spec 一致即可），內容：
   - 修改了哪些檔案（列出路徑）
   - 每個驗收條件的完成狀態
   - 遇到的問題與處理方式（若有）
   回報以檔案為準——你的最終回覆訊息可能不會送達主線，不要只靠回覆。
```

**`--tdd` 模式且該 chunk 非豁免時**，在上面的執行要求後追加（豁免 chunk 不加）：

```
7. TDD 順序（不可跳過、不可對調）：
   a. 紅燈：先只寫 spec「測試案例」列出的測試，執行並確認失敗，且失敗原因是功能尚未實作。
      測試一開始就通過 → 改寫測試；失敗原因是測試寫錯 → 先修測試。
   b. 綠燈：寫最少的實作讓測試通過，不可修改測試斷言來讓它通過。
   c. 回歸：依上面第 5 點的測試範圍跑相關測試，確認沒有失敗（完整測試由主線統一跑）。
   d. 回報檔加一節「TDD 證據」：紅燈、綠燈各附執行指令與輸出結尾約 10 行。
```

### 2-3 收集執行結果

**回報以檔案為準**：等同批次所有 agents 完成後，用 Read 讀取各 `.just-do-it/chunk-{N}-report.md` 收結果。**不依賴 agent 的回覆訊息、禁止用 SendMessage 向執行中的 agent 索取結果**——實測（2026-07-29）背景 agent 的回覆與完成通知都可能只剩 idle 空殼，只有寫進檔案的回報保證拿得到。

**不信任驗證**：Phase 2 開始前先記錄 `git status` baseline（非 git 專案則記錄影響範圍的檔案清單）；收完回報後用 `git diff --stat` 對照各 chunk 宣稱的檔案清單——多改、漏改、report 檔缺失都當場現形。

**chunk 失敗處理**：report 檔缺失或內容顯示失敗 → 帶失敗原因重派一次；再失敗 → 停止該 chunk，列入最終報告「需要人工處理」。

顯示即時進度：

```
⚡ Phase 2 執行中

批次 1：
  ✅ Chunk 1: DB Schema — 完成（3 個檔案）
  ✅ Chunk 2: 資料模型 — 完成（1 個檔案）

批次 2：
  ✅ Chunk 3: API 實作 — 完成（5 個檔案）
  ⚠️  Chunk 4: 前端元件 — 完成但有警告（見下方）
```

彙整每個 chunk 的：
- 完成狀態（完成 / 部分完成 / 失敗）
- 修改的檔案列表
- 未完成的驗收條件（若有）
- 遭遇的問題（若有）

## Phase 3：Code Review + 測試驗收

### 3-0 契約核對（僅當 spec 含「介面契約」區塊時執行）

確定性檢查，純 Grep、零 token。spec 沒有「介面契約」區塊（路徑 B/C 常見）→ 整節跳過，直接進 3-1。

**核對項目：**

1. **識別名落地**：「本次新增／變更」區的每個識別名，用 Grep 逐一比對本次修改的檔案 → 必須出現且拼寫完全一致（含大小寫）
2. **既有介面未被破壞**：「既有介面（不可破壞）」區的每個簽名，用 Grep 確認未被修改（契約表標注★變更者除外）
3. **DTO 欄位一致**：契約表列出的 DTO 欄位名，逐一存在於對應類別中

**不符處理（核對→修正→重核迴圈）：**

spawn 一個 fix agent（**同步執行，`run_in_background: false`**，循序步驟無並行需求），prompt：

```
你是一個 Fix agent，以下實作偏離了 spec 的介面契約，請修正：

契約偏差清單：
[列出：契約要求的識別名/簽名 vs 實作中的現況，逐筆對照]

介面契約（以此為準）：
[貼入 spec 的「介面契約」區塊全文]

要求：只把實作改回契約表的命名與簽名。不要修改契約表本身、不要動其他邏輯。
若你認為是契約有誤而非實作有誤，不要擅自改名，回報理由即可。
完成後列出變更的檔案。
```

修正後重新執行核對。**上限 2 輪**（核對本身零 token，比 3-3 的 1 輪寬）；仍不符 → 列入最終報告「需要人工處理」，並標明判斷：是實作該改、還是契約疑似有誤待人裁決。

★ 通過 3-0 後才進 3-1。命名與簽名一致性已由本節保證，Code Review agent 專注邏輯品質。

### 3-0b TDD 證據核對（僅 `--tdd` 模式）

對每個非豁免 chunk 的回報檔檢查：

1. 有「TDD 證據」一節，紅燈輸出確實是**失敗**、綠燈輸出確實是**通過**
2. 紅燈的失敗原因是功能尚未實作，不是語法錯、import 錯或環境錯
3. 用 `git diff` 確認 spec 列出的測試檔確實存在且被修改

任一不符 → 視為該 chunk 失敗，套用 2-3 的失敗處理（帶原因重派一次）。

3-1 的 Code Review prompt 審查重點另加一條：「測試是否真的驗證了驗收條件，而不是空洞斷言（例如只檢查不是 null、assert true）」。

### 3-1 Code Review

Spawn 一個 `general-purpose` review agent。**必須同步執行（`run_in_background: false`）、不取名字**——Agent 工具的回傳值就是審查報告，同步執行讓報告送達成為原子操作。

> 為什麼強制同步（2026-07-29 實際踩坑）：review agent 曾被背景執行＋SendMessage 輪詢，結果它做完的完整 NEEDS_FIX 報告只留在自己的 transcript 裡，orchestrator 只收到兩次 idle 空通知，17 分鐘的驗證全部作廢、review 被重做一遍。review 是單線步驟，同步執行沒有任何代價。

prompt：

```
你是一個 Code Review agent，請針對以下實作進行嚴格審查。

═══════════════════════════════════════
任務 Spec：
[貼入 just-do-it-spec.md 全文]

═══════════════════════════════════════
各 Chunk 執行結果摘要：
[貼入 Phase 2 的執行結果]

═══════════════════════════════════════
本次實際變更：
[貼入 git diff --stat（或變更檔案清單），讓你不必自己摸哪些檔案動過]

═══════════════════════════════════════
審查重點（依優先序）：
1. **驗收條件覆蓋率**：spec 中每個驗收條件是否都有對應的實作？
2. **整合正確性**：各 chunk 之間的介面是否一致？有無漏接或命名不符？
3. **程式碼品質**：是否有明顯的 bug、安全問題、效能問題？
4. **邊界條件**：是否處理了空值、例外、錯誤路徑？
5. **不破壞現有功能**：修改是否可能影響未在 spec 中提到的現有功能？

回傳格式（必須是以下兩種之一）：

APPROVED
[簡短說明實作品質良好的理由，一段話]

或

NEEDS_FIX
問題清單：
- [問題 1]：[具體說明] → 建議修改方式
- [問題 2]：[具體說明] → 建議修改方式
```

### 3-2 執行測試驗收

**完整測試在這裡統一跑**：Phase 2 的 chunk agents 只跑各自相關的測試（見 2-2 第 5 點），主線在所有 chunk 收齊後跑一次完整測試。循序的多步驟任務（例如每步 commit 一次的大範圍搬檔），每步結束時主線仍跑一次完整測試再 commit，確保每個 commit 都是綠的。

偵測專案測試框架並執行：

| 技術棧 | 偵測方式 | 測試指令 |
|--------|---------|---------|
| Node.js | `package.json` 有 `test` script | `npm test` |
| Node.js (Jest) | `jest.config.*` 存在 | `npx jest` |
| Python | `pytest.ini` / `pyproject.toml` 有 pytest | `pytest` |
| Java (Maven) | `pom.xml` 存在 | `mvn test -q` |
| Java (Gradle) | `build.gradle` 存在 | `./gradlew test` |
| .NET | `*.csproj` / `*.sln` 存在 | `dotnet test` |
| Go | `*_test.go` 存在 | `go test ./...` |

**驗收階梯（fallback，逐級往下找到能跑的為止，「跳過」是最後手段）：**

1. **測試**：上表的測試指令
2. **type-check**：`tsc --noEmit` / `mypy` / 依技術棧
3. **build／編譯**：`npm run build` / `mvn -q compile` / `./gradlew compileJava` / `dotnet build`
4. **語法檢查**：`python -m compileall` / 依技術棧
5. 全都沒有 → 才在報告「未執行／無法驗收」區標注原因

「無測試框架 → 直接跳過」等於零驗收就宣告完成（2026-07-29 實測踩坑），禁止。

**驗收指令必須非互動**：執行前先確認指令不會進入互動模式（常見地雷：`next lint` 未初始化會跳設定選單、`npm init`）。指令若需要初始化設定檔，**不得擅自初始化**（會新增設定檔、超出任務範圍），標記為「無法驗收」並寫明原因。

### 3-3 問題修復（最多 1 輪）

**主線直修路徑**：無論問題來自 Code Review 還是主線自己發現，修改範圍 ≤2 個檔案且 ≤20 行 → 主線直接修，不 spawn fix agent（省一次往返），但必須記入最終報告的修復輪區塊。超過此範圍才走 fix agent。

**若 Code Review 回傳 NEEDS_FIX：**

spawn 一個 fix agent（同步執行，`run_in_background: false`）處理所有列出的問題：

```
你是一個 Fix agent，根據以下 Code Review 意見進行修正。

Review 意見：
[貼入 NEEDS_FIX 的問題清單]

原始 Spec：
[貼入 just-do-it-spec.md]

要求：只修正 Review 指出的問題，不要做額外的修改。完成後列出變更的檔案。
```

修復後重新執行 Code Review 一次。若仍為 NEEDS_FIX → 在最終報告中列出未解決問題，標記需要人工處理。

**若測試失敗：**

spawn 一個 fix agent（同步執行，`run_in_background: false`）修復失敗的測試：

```
你是一個 Fix agent，以下測試執行失敗，請修復：

失敗測試輸出：
[貼入測試失敗訊息]

原始 Spec：
[貼入 just-do-it-spec.md]

要求：讓測試通過，不要修改測試邏輯本身（除非測試本身有 bug）。
```

修復後重跑測試一次。若仍失敗 → 在最終報告中列出失敗項目，標記需要人工處理。

```

**若有未解決問題，額外顯示：**

```

## 注意事項

- **不詢問確認**：收到描述後直接執行，不等使用者二次確認
- **不可逆操作例外（安全底線，凌駕上一條）**：`git commit`／`git push`／部署／刪除檔案，一律停下來交回使用者決定。Phase 4 出完報告即停，不自行 commit 或 push（部分專案 push main 會直接觸發 CI/CD 上生產）
- **subagent 通訊鐵律**：並行的 chunk agents 背景執行、回報一律寫 `.just-do-it/` 檔案由主線 Read 收取；review／fix agent 一律同步執行（`run_in_background: false`）。**任何情況下都不用 SendMessage 向 subagent 要結果**——那條路只會拿到 idle 通知，拿不到報告
- **chunk 之間的相依要嚴格控制**：相依的 chunk 一定要在前置 chunk 完成後才 spawn
- **每個 subagent 只負責自己的 chunk 範圍**，不要越界修改
- **fix 輪數上限 1 輪**：超過 1 輪的問題標記為人工處理，不要無限循環
- **spec 檔案路徑**：`just-do-it-spec.md` 放在執行 skill 時的當前工作目錄；寫檔前若已存在，先歸檔（見 1-3 覆寫保護）
- **兩層門檻，管不同層**：整個任務 ≤3 個檔案 → 根本不進本 skill，直接做（全域 CLAUDE.md 路由層）；進了本 skill 之後，單一 chunk ≤1 個檔案且 ≤30 行 → 主線直接做，不 spawn subagent（chunk 層）
- **`.just-do-it/` 是暫存目錄**：回報檔用完即棄，結束時提示使用者可刪除
- **版控歸屬**：`.just-do-it/` 與 `just-do-it-spec.md` 加入 `.gitignore`（單次任務暫存物）；`CONTEXT.md`、`INTERFACES.md`、`docs/specs/` 則應進版控（長存知識資產）。首次遇到未設定的專案時一併處理並告知使用者
