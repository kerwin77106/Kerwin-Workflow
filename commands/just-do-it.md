# Just Do It — 全自動任務執行

不問、不等、不停。收到任務描述後自動完成所有事情。

**完整流程：**
```
Phase 1: Spec 生成（自動，無需確認）
Phase 2: Chunk 並行執行（subagents 分工）
Phase 3: Code Review + 測試驗收
Phase 4: 最終報告
```

---

## Phase 1：Spec 偵測 + 生成

### 1-1 偵測是否已有 Spec

**依序執行以下偵測，任一命中即停止：**

**偵測 A — 對話 context**
回顧當前對話，判斷使用者是否已提供明確的任務內容，符合以下任一條件即視為「已有 spec」：
- 對話中出現了明確的任務清單（例如：剛列出的 TODO 項目、OPT-XXX 清單）
- 對話中有 spec 文件的完整或部分內容
- 使用者說「做 XXX 幾項」、「完成上面這些」、「照剛才列的去做」

**偵測 B — 檔案系統**
用 Glob 掃描當前目錄，查找 spec 類檔案（優先序由上到下）：
- `just-do-it-spec.md`
- `*SPEC*.md`、`*spec*.md`（如 `OPT-SPEC.md`）
- `TODO.md`、`todo.md`
- `implementation_plan.md`
- `*plan*.md`、`*PLAN*.md`

### 1-2 根據偵測結果決定路徑

**關鍵區分：任務清單 ≠ Spec**

| 類型 | 特徵 | 處理方式 |
|------|------|---------|
| **完整 Spec** | 有具體檔案路徑 + 驗收條件 + 實作細節 | 直接跳 Phase 2 |
| **任務清單** | 只有項目名稱/描述，無檔案路徑 | 快速 Phase 1（以清單為起點補全） |
| **什麼都沒有** | 只有模糊的需求描述 | 完整 Phase 1（從頭分析） |

```
路徑 A — 完整 Spec（跳過生成）
├── 偵測到：有明確檔案路徑 + 驗收條件的 spec 文件（檔案或對話中）
├── 使用者有指定範圍 → 篩出對應 chunks
├── 未指定範圍 → 全部執行，不限數量
└── 顯示：
    📋 偵測到完整 Spec：[來源]
       本次執行：[項目清單]，共 {N} 個 chunks
       直接進入執行...

路徑 B — 任務清單（快速 Phase 1）
├── 偵測到：對話或檔案中有任務清單，但只有名稱/描述，無實作細節
├── 以清單為起點，針對每個任務：
│   - 用 Grep/Glob 定位相關檔案和程式碼位置
│   - 根據程式碼現況擬定驗收條件
│   - 產出完整 just-do-it-spec.md
├── 使用者有指定範圍 → 只對選定項目做上述分析
└── 顯示：
    📋 偵測到任務清單：[來源]，共 {N} 項
       進行快速 Spec 分析（補全檔案路徑與驗收條件）...
       [分析完成後]
    📄 Spec 已產出：just-do-it-spec.md，共 {N} 個 chunks
       開始執行...

路徑 C — 無 Spec（完整 Phase 1）
└── 走 1-3 從頭分析
```

### 1-3 重新生成 Spec（僅在未偵測到 spec 時執行）

讀取專案上下文：
1. 偵測技術棧（依序讀取：`package.json` / `pom.xml` / `build.gradle` / `pyproject.toml` / `requirements.txt` / `*.csproj` / `CLAUDE.md`）
2. 用 Glob 掃描專案結構（忽略 `node_modules/`、`.git/`、`dist/`、`build/`、`target/`）
3. 用 Grep 搜尋與任務描述相關的現有程式碼

將以下內容寫入 `just-do-it-spec.md`（放在當前目錄）：

```markdown
# [任務名稱] — Just Do It Spec

## 目標
（一句話描述要達成什麼）

## 背景
（為什麼需要做這個，現有功能現況）

## 技術範圍
- 技術棧：
- 主要影響模組/檔案：

## Task Chunks

### Chunk 1: [名稱]
**目的**：
**需要新增/修改的檔案**：
- `path/to/file` — 說明要做什麼

**驗收條件**：
- [ ] 條件 1
- [ ] 條件 2

**相依**：無（可並行）/ Chunk N 完成後才開始

---

### Chunk 2: [名稱]
（同上格式）

---

## 整合驗收條件
- [ ] 所有 chunk 完成後的整體驗收項目
- [ ] 測試通過
- [ ] 不破壞現有功能
```

### 1-4 Chunk 設計原則

- **單一職責**：每個 chunk 只做一件清楚定義的事（DB schema / API 實作 / 前端元件 / 測試）
- **最小化相依**：盡量讓 chunks 可以並行執行
- **有相依性的 chunks** 標記清楚，分批執行
- **chunk 數量**：不限上限。太小（只有 1 步驟、改 1 個檔案）直接做不用拆；多項任務照單全收，由使用者自行判斷複雜度
- **每個 chunk 必須包含明確的驗收條件**，方便後續 Review

產出 spec 後顯示：
```
📄 Spec 已產出：just-do-it-spec.md
   共 {N} 個 chunks，{X} 批並行執行
   開始執行...
```

## Phase 2：並行執行

### 2-1 分析相依順序，排定批次

分析 spec 中各 chunk 的相依關係，分成多個「執行批次」：

- 無相依的 chunks → 同一批次，並行執行
- 有相依的 chunks → 等前置批次完成後才執行

範例：
```
批次 1（並行）：Chunk 1（DB Schema）、Chunk 2（資料模型）
批次 2（並行）：Chunk 3（API 實作）、Chunk 4（前端元件）— 相依批次 1
批次 3（循序）：Chunk 5（整合測試）— 相依批次 2
```

### 2-2 Spawn Subagents

**每個 chunk 各 spawn 一個 `general-purpose` subagent**，同一批次的 agents 同時送出（並行）。

每個 subagent 的 prompt 結構：

```
你是一個實作 agent，負責完成以下任務 chunk。請閱讀 Spec 後直接執行，不需要確認。

═══════════════════════════════════════
你負責的 Chunk：
[貼入對應 chunk 的完整規格]

═══════════════════════════════════════
完整 Spec（供參考上下文）：
[貼入 just-do-it-spec.md 全文]

═══════════════════════════════════════
執行要求：
1. 按照「驗收條件」逐一完成，每條完成後在心中打勾
2. 只修改此 chunk 規格中列出的檔案範圍
3. 若發現需要動到 chunk 範圍外的檔案，先做必要的最小修改，並在回報中說明原因
4. 完成後回報：
   - 修改了哪些檔案（列出路徑）
   - 每個驗收條件的完成狀態
   - 遇到的問題與處理方式（若有）
```

### 2-3 收集執行結果

等待同批次所有 agents 完成，顯示即時進度：

```
⚡ Phase 2 執行中

批次 1：
  ✅ Chunk 1: DB Schema — 完成（3 個檔案）
  ✅ Chunk 2: 資料模型 — 完成（1 個檔案）

批次 2：
  ✅ Chunk 3: API 實作 — 完成（5 個檔案）
  ⚠️  Chunk 4: 前端元件 — 完成但有警告（見下方）
```

彙整每個 chunk 的：
- 完成狀態（完成 / 部分完成 / 失敗）
- 修改的檔案列表
- 未完成的驗收條件（若有）
- 遭遇的問題（若有）

## Phase 3：Code Review + 測試驗收

### 3-0 契約核對（僅當 spec 含「介面契約」區塊時執行）

確定性檢查，純 Grep、零 token。spec 沒有「介面契約」區塊（路徑 B/C 常見）→ 整節跳過，直接進 3-1。

**核對項目：**

1. **識別名落地**：「本次新增／變更」區的每個識別名，用 Grep 逐一比對本次修改的檔案 → 必須出現且拼寫完全一致（含大小寫）
2. **既有介面未被破壞**：「既有介面（不可破壞）」區的每個簽名，用 Grep 確認未被修改（契約表標注★變更者除外）
3. **DTO 欄位一致**：契約表列出的 DTO 欄位名，逐一存在於對應類別中

**不符處理（核對→修正→重核迴圈）：**

spawn 一個 fix agent，prompt：

```
你是一個 Fix agent，以下實作偏離了 spec 的介面契約，請修正：

契約偏差清單：
[列出：契約要求的識別名/簽名 vs 實作中的現況，逐筆對照]

介面契約（以此為準）：
[貼入 spec 的「介面契約」區塊全文]

要求：只把實作改回契約表的命名與簽名。不要修改契約表本身、不要動其他邏輯。
若你認為是契約有誤而非實作有誤，不要擅自改名，回報理由即可。
完成後列出變更的檔案。
```

修正後重新執行核對。**上限 2 輪**（核對本身零 token，比 3-3 的 1 輪寬）；仍不符 → 列入最終報告「需要人工處理」，並標明判斷：是實作該改、還是契約疑似有誤待人裁決。

★ 通過 3-0 後才進 3-1。命名與簽名一致性已由本節保證，Code Review agent 專注邏輯品質。

### 3-1 Code Review

Spawn 一個 `general-purpose` review agent，prompt：

```
你是一個 Code Review agent，請針對以下實作進行嚴格審查。

═══════════════════════════════════════
任務 Spec：
[貼入 just-do-it-spec.md 全文]

═══════════════════════════════════════
各 Chunk 執行結果摘要：
[貼入 Phase 2 的執行結果]

═══════════════════════════════════════
審查重點（依優先序）：
1. **驗收條件覆蓋率**：spec 中每個驗收條件是否都有對應的實作？
2. **整合正確性**：各 chunk 之間的介面是否一致？有無漏接或命名不符？
3. **程式碼品質**：是否有明顯的 bug、安全問題、效能問題？
4. **邊界條件**：是否處理了空值、例外、錯誤路徑？
5. **不破壞現有功能**：修改是否可能影響未在 spec 中提到的現有功能？

回傳格式（必須是以下兩種之一）：

APPROVED
[簡短說明實作品質良好的理由，一段話]

或

NEEDS_FIX
問題清單：
- [問題 1]：[具體說明] → 建議修改方式
- [問題 2]：[具體說明] → 建議修改方式
```

### 3-2 執行測試驗收

偵測專案測試框架並執行：

| 技術棧 | 偵測方式 | 測試指令 |
|--------|---------|---------|
| Node.js | `package.json` 有 `test` script | `npm test` |
| Node.js (Jest) | `jest.config.*` 存在 | `npx jest` |
| Python | `pytest.ini` / `pyproject.toml` 有 pytest | `pytest` |
| Java (Maven) | `pom.xml` 存在 | `mvn test -q` |
| Java (Gradle) | `build.gradle` 存在 | `./gradlew test` |
| .NET | `*.csproj` / `*.sln` 存在 | `dotnet test` |
| Go | `*_test.go` 存在 | `go test ./...` |

若無測試框架 → 跳過，在報告中標注「⚠️ 無測試框架，跳過測試驗收」。

### 3-3 問題修復（最多 1 輪）

**若 Code Review 回傳 NEEDS_FIX：**

spawn 一個 fix agent 處理所有列出的問題：

```
你是一個 Fix agent，根據以下 Code Review 意見進行修正。

Review 意見：
[貼入 NEEDS_FIX 的問題清單]

原始 Spec：
[貼入 just-do-it-spec.md]

要求：只修正 Review 指出的問題，不要做額外的修改。完成後列出變更的檔案。
```

修復後重新執行 Code Review 一次。若仍為 NEEDS_FIX → 在最終報告中列出未解決問題，標記需要人工處理。

**若測試失敗：**

spawn 一個 fix agent 修復失敗的測試：

```
你是一個 Fix agent，以下測試執行失敗，請修復：

失敗測試輸出：
[貼入測試失敗訊息]

原始 Spec：
[貼入 just-do-it-spec.md]

要求：讓測試通過，不要修改測試邏輯本身（除非測試本身有 bug）。
```

修復後重跑測試一次。若仍失敗 → 在最終報告中列出失敗項目，標記需要人工處理。

## Phase 4：最終報告

顯示完整摘要：

```
🎉 Just Do It — 完成！

📋 任務：[任務名稱]
📄 Spec：just-do-it-spec.md

── 執行結果 ─────────────────────────────
  ✅ Chunk 1: [名稱] — [N 個檔案]
  ✅ Chunk 2: [名稱] — [N 個檔案]
  ✅ Chunk 3: [名稱] — [N 個檔案]

── 審查結果 ─────────────────────────────
  ✅ Code Review — APPROVED
  ✅ 測試 — 12/12 通過
  （或 ⚠️ 無測試框架）

── 變更檔案 ─────────────────────────────
  新增：
    src/xxx.ts
    src/yyy.ts
  修改：
    src/zzz.ts
```

**若有未解決問題，額外顯示：**

```
── ⚠️ 需要人工處理 ──────────────────────
  - [問題描述 1]
  - [問題描述 2]
  建議：/just-do-it 再次執行，或手動修復後呼叫 /review 驗收
```

## 注意事項

- **不詢問確認**：收到描述後直接執行，不等使用者二次確認
- **chunk 之間的相依要嚴格控制**：相依的 chunk 一定要在前置 chunk 完成後才 spawn
- **每個 subagent 只負責自己的 chunk 範圍**，不要越界修改
- **fix 輪數上限 1 輪**：超過 1 輪的問題標記為人工處理，不要無限循環
- **spec 檔案路徑**：`just-do-it-spec.md` 放在執行 skill 時的當前工作目錄
- 若任務描述非常小（只有一個步驟、改一個檔案）→ 不需要拆 chunk，直接執行，不使用 subagent
