# Make Spec — 規格精煉器

**定位**：不從零發明需求（那是討論階段的事），把已經跟使用者討論好的結論，精煉成介面命名鎖死、可直接施工或交付的規格。

**核心價值**：介面契約在施工前釘死。並行實作的 subagent 不會各自發明類別名、方法名、欄位名；給客戶看的文件和自己實作的程式碼指向同一份事實。

## 三層知識棧

| 檔案 | 位置 | 回答的問題 | 生命週期 |
|------|------|-----------|---------|
| `CONTEXT.md` | 專案根目錄 | 名詞是什麼意思（業務層） | 長存，越用越厚 |
| `INTERFACES.md` | 專案根目錄 | 介面長什麼樣（技術層） | 長存，越用越厚 |
| `just-do-it-spec.md` | 當前目錄 | 這次怎麼做（施工層） | 用完即棄 |
| `~/.claude/spec-lessons.md` | 使用者家目錄 | 產 spec 犯過什麼錯 | 長存，跨專案共用 |

以上檔案**不存在時一律靜默跳過，不報錯**；要寫入而檔案不存在時，先徵求使用者同意才建立。

---

## 使用方式

```
/make-spec              ← 從當前對話結論產 spec（預設出口 A：施工規格）
/make-spec --sa         ← 出口 B：SA 規格文件（會再問客戶版或工程師版）
/make-spec --close      ← 完工回寫：比對實作與台帳，更新狀態
```

## 流程總覽

```
步驟 0 收集輸入（對話結論 + 三層知識棧）
   ↓
步驟 1 討論補齊（僅在討論不充分時進入）
   ↓
步驟 2 掃專案（技術棧／命名慣例／增量判定）
   ↓
步驟 3 推導契約表 → ★確認閘門（唯一互動閘門 = 使用者的 SA 簽核）
   ↓                └ 順便收詞 → CONTEXT.md
分叉 ├─ 出口 A → just-do-it-spec.md → 使用者自行呼叫 /just-do-it
     └─ 出口 B → SA 規格文件（客戶版／工程師版）
   ↓
步驟 5 0-token 自我驗證
   ↓
步驟 6 寫入介面台帳（狀態＝計畫中）
   ↓
（施工完成後）/make-spec --close → 台帳狀態＝已實作 + 提議記 lesson
```

## 步驟 0：收集輸入

1. **主要輸入 = 當前對話的討論結論**。使用者跟 Claude 討論出的需求、決策、取捨，就是本指令的原料——不要拋開對話重新解讀需求。
2. 讀取知識資產（存在才讀）：
   - 專案根目錄 `CONTEXT.md` → 術語字典，後續命名一律以它為準
   - 專案根目錄 `INTERFACES.md` → 介面台帳，增量任務的既有介面來源
   - `~/.claude/spec-lessons.md` → 過去產 spec 的教訓，相關者納入本次注意事項
3. **判斷討論充分度**：對話是否已涵蓋「目標、範圍（含範圍外）、主要流程」三件事？
   - 已充分 → 直接進步驟 2
   - 不足 → 進步驟 1 補齊（缺哪塊補哪塊，不從頭來過）

## 步驟 1：討論補齊（需要時才進入）

### 討論紀律

1. **一次只問一題**，等回答再前進。
2. **每題必附推薦答案 + 理由 + 詳細說明**。專有名詞必須解釋，不預設使用者懂術語——看不懂術語就無法真正做決策。
3. **事實自己查，只問決策**。用 Grep／Read 查得到的（現有程式碼行為、檔案結構、設定值）自己查，只把需要使用者拍板的取捨拿出來問。
4. **按決策依賴順序問**：先問會影響後續問題的。
5. **架構級決策不問單題**。影響 3 個以上契約、或事後難回頭的決策，攤 2–3 個方案並排（各附權衡與推薦）讓使用者選。

### 術語紀律（domain-modeling 四行為）

- 使用者的用詞跟 `CONTEXT.md` 衝突 → 當場指出：「字典裡 X 的定義是…，你現在說的像 Y，是哪個？」
- 模糊詞、多義詞 → 提議正式詞：「你說『帳號』——是 Customer 還是 User？這是兩個東西」
- 用具體情境壓力測試概念邊界：「如果員工請假到一半銷假，這是狀態變化還是一張新單？」
- 使用者的說法跟程式碼現況矛盾 → 當場對質：「你說可以部分取消，但 code 是整單取消，哪個對？」

### 收斂檢查（spec 成形前過一遍）

資料流／錯誤處理／邊界條件／測試策略——四個面向各自問過自己「這塊討論到了嗎」，沒有就補問。

## 步驟 2：掃專案

1. **技術棧偵測**：依序讀 `package.json` / `pom.xml` / `build.gradle` / `pyproject.toml` / `requirements.txt` / `*.csproj` / 專案 `CLAUDE.md`。
2. **命名慣例**：讀 1–2 個同類既有檔案（既有的 Service、Controller），契約命名跟隨專案現況，不引入新風格。
3. **增量判定**（本次任務動到既有模組時）：
   - 從 `INTERFACES.md` 撈出相關介面，**並用 Grep 對實碼確認仍成立**（台帳可能過時；矛盾時以 code 為準，順手更新台帳並告知使用者）
   - 台帳沒有但 code 有的介面 → **懶建**：只把本次任務會碰到的介面補進台帳，不做全專案反向工程
4. 對照 `spec-lessons.md`，把相關教訓列入本次注意事項。

## 步驟 3：推導契約表 → ★確認閘門

### 契約表格式（兩區）

**契約類型**（依專案語言選用）：
- OOP 語言：`ENTITY_CLASS`、`REPOSITORY_CLASS`、`SERVICE_INTERFACE`、`METHOD_SIGNATURE`、`DTO_CLASS`、`API_ENDPOINT`
- 函式導向：`MODULE_INTERFACE`、`FUNCTION_SIGNATURE`、`DATA_MODEL`

```markdown
## 介面契約

### 既有介面（不可破壞）
| 類型 | 識別名 | 定義 | 備註 |
|------|--------|------|------|
| METHOD_SIGNATURE | LeaveService.apply(LeaveRequest):LeaveResponse | 既有請假申請入口 | 3 處呼叫端 |

### 本次新增／變更
| 類型 | 識別名 | 定義 | 狀態 |
|------|--------|------|------|
| METHOD_SIGNATURE | LeaveService.revoke(Long leaveId):void | 銷假 | 新增 |
| METHOD_SIGNATURE | LeaveService.apply(LeaveRequest, boolean urgent):LeaveResponse | 加急件參數 | ★變更：需同步修改 3 處呼叫端 |

### DTO 欄位定義
**LeaveRequest**
| 欄位 | 型別 | 可空 | 說明 |
|------|------|------|------|
| employeeId | Long | 否 | 員工 ID |
| startDate | LocalDate | 否 | 起日 |
```

### 閘門（使用者的 SA 簽核時刻）

把契約表完整攤給使用者確認。這是**唯一的互動閘門**——契約層出錯代價高（照著錯的做＝全部重做），chunk 層代價低（錯一個重做一個），所以人的注意力集中在這裡。命名有誤當場改，改完才往下走。

### 收詞（併入同一次閘門，不加互動成本）

契約表裡出現的新業務概念＝候選詞條。確認契約表時順便列出：「這 N 個新術語要進 CONTEXT.md 嗎？」使用者同意才寫入。`CONTEXT.md` 不存在時先問要不要建立。

詞條格式（只當字典用，不放實作細節）：

```markdown
**Leave（請假單）**:
員工提出的單次請假申請，含起訖日期與事由。
_Avoid_: LeaveApplication, AbsenceForm, 假勤申請
```

## 步驟 4-A：出口 A — 施工規格（預設）

寫入 `just-do-it-spec.md`（當前目錄）。**格式必須命中 /just-do-it 的「路徑 A：完整 Spec」判定**（有具體檔案路徑 + 驗收條件），讓它直接跳 Phase 2 並行執行，不重跑 spec 生成。

```markdown
# [任務名稱] — Just Do It Spec

## 目標
（一句話）

## 背景
（為什麼做、現況）

## 技術範圍
- 技術棧：
- 主要影響模組/檔案：

## 介面契約（鎖定，不可偏離）

（貼入步驟 3 確認後的完整契約表：既有區＋新增/變更區＋DTO 欄位）

★ 所有 chunk 必須嚴格使用上表命名，不可自行發明類別名／方法名／欄位名。
★ 「既有介面（不可破壞）」區的簽名一律不准修改（標注★變更者除外）。
★ 若實作中發現契約有誤或不足 → 停止並回報，不要自行改名。

## Task Chunks

### Chunk 1: [名稱]
**目的**：
**需要新增/修改的檔案**：
- `src/main/java/.../LeaveService.java` — 說明
**本 chunk 涉及的契約**：
- METHOD_SIGNATURE: LeaveService.revoke(Long leaveId):void
**驗收條件**：
- [ ] 條件 1
**相依**：無（可並行）/ Chunk N 完成後才開始

## 整合驗收條件
- [ ] 契約比對：契約表每個識別名都出現在實作中且拼寫一致
- [ ] 「既有介面」區未被修改（標注★變更者除外，且其呼叫端已同步）
- [ ] 測試通過
- [ ] 不破壞現有功能
- [ ] 完工後執行 /make-spec --close 回寫台帳
```

寫完顯示摘要：契約 N 筆（既有 X／新增 Y／變更 Z）、chunk M 個，提示可執行 `/just-do-it`。

## 步驟 4-B：出口 B — SA 規格文件（--sa）

先問一題：**客戶版還是工程師版？**

| | 客戶版 | 工程師版 |
|---|--------|---------|
| 語言 | 業務語言，術語附白話解釋 | 技術語言 |
| 契約 | 只含對接會用到的 API 表面 | 完整契約表 + DTO 欄位 + 依賴關係 |
| 隱藏 | 內部類別名、方法簽名 | 不隱藏 |

共同結構：摘要／背景／功能清單（含驗收條件）／主要流程／API 規格／資料模型／非功能需求／範圍外／假設條件。術語一律用 `CONTEXT.md` 的正式詞。

寫入 `{slug}-spec-sa.md`（當前目錄）。完成後提示：可再轉 Word（claude-office-skills）或同步 Notion——**只提示，不自動執行**。

出口 B 不產 chunk、不含檔案路徑（客戶不在乎，其他工程師會自己規劃）。

## 步驟 5：0-token 自我驗證（產出後立即執行）

| # | 檢查 | 方法 | 失敗處理 |
|---|------|------|---------|
| 1 | 契約認領 | 新增/變更區每個識別名至少被一個 chunk 的「涉及契約」列出 | 漏認領＝漏工，補 chunk 或回報 |
| 2 | 同義詞封殺 | 契約識別名比對 CONTEXT.md 各詞條 _Avoid_ 清單 | 用到被封殺詞＝警告並改名 |
| 3 | 路徑存在性 | 標「修改」的檔案路徑用 Glob 驗證存在；標「新增」的驗證父目錄存在 | 路徑錯＝修正 |

（出口 B 只做檢查 2。）能自行修正的修正後重驗一次；改不動的列給使用者。

## 步驟 6：寫入介面台帳

`INTERFACES.md`（專案根目錄）格式：

```markdown
# 介面台帳

## LeaveService（請假模組）
| 類型 | 識別名 | 定義 | 狀態 | 來源任務 | 更新日 |
|------|--------|------|------|---------|--------|
| METHOD_SIGNATURE | LeaveService.apply(...) | 請假申請入口 | 已實作 | leave-mgmt | 2026-07-01 |
| METHOD_SIGNATURE | LeaveService.revoke(...) | 銷假 | 計畫中 | leave-revoke | 2026-07-29 |
```

狀態：`計畫中` → `已實作` → `已棄用`。本次新增/變更的契約以「計畫中」寫入。台帳不存在時先問是否建立。

---

## /make-spec --close — 完工回寫

1. 讀台帳所有「計畫中」項目
2. 逐項 Grep 實碼比對（識別名、簽名是否一致）
3. 相符 → 狀態改「已實作」，更新日期
4. 不符 → 列出差異問使用者：**改 code 對齊台帳，還是改台帳承認現況？** 不擅自二選一
5. 若本次施工暴露了 spec 缺陷 → 走 lesson 捕捉（見下）

## spec-lessons.md — 教訓庫

位置：`~/.claude/spec-lessons.md`（跨專案共用，**不放專案 repo 內**）。格式：

```markdown
| 日期 | 症狀 | 根因 | 下次怎麼避免 |
|------|------|------|-------------|
| 2026-07-29 | subagent 自行改了 DTO 欄位名 | 契約表沒列該 DTO 的欄位 | DTO 一律列全欄位，不只列類名 |
```

**捕捉時機（主動提議制，使用者點頭才存）**：
- (a) `--close` 或 just-do-it 執行後發現 spec 缺陷（chunk 漏檔案、契約粒度不夠、措辭被誤解）
- (b) 使用者在步驟 3 閘門大幅修改推導出的契約（代表推導邏輯有系統性偏差）

擬好「症狀／根因／下次怎麼避免」再提議，不擅自寫入。首次建檔先問。

## 與 /just-do-it 的交接

- 輸出格式設計成命中其 Phase 1 路徑 A（有檔案路徑＋驗收條件→直接跳 Phase 2）。
- 契約遵守三道保險：
  1. **預防**：spec 內的 ★ 警告（會被貼進每個 subagent 的 prompt）
  2. **偵測＋自動修正**：just-do-it Phase 3-0 契約核對——確定性 Grep 檢查（識別名落地／既有介面未破壞／DTO 欄位一致），不符則核對→修正→重核迴圈（上限 2 輪）
  3. **最後把關**：整合驗收條件的契約比對
- 分工原則：**正確性在施工迴圈內由 3-0 強制到位（機器）；`--close` 只管帳（人）**——台帳狀態翻轉、差異仲裁、lesson 提議，都需要使用者在場。
- subagent prompt（預防端）維持不動；實測若預防端明顯不足再調整。

## 邊界情況

- **對話中沒有任何討論就呼叫** → 進步驟 1 從頭討論（等同輕量需求訪談），不拒絕
- **任務太小**（1 個檔案、1 個步驟）→ 提示不需要 spec，直接做即可
- **台帳與 code 矛盾** → 以 code 為準，更新台帳並告知
- **使用者在閘門大改契約** → 完成本次後走 lesson 捕捉 (b)
- **CONTEXT.md／INTERFACES.md／spec-lessons.md 不存在** → 讀取時靜默跳過；寫入時先徵求同意

## 注意事項

- 全程繁體中文
- 唯一互動閘門在步驟 3（契約表確認）；--sa 多一題版本選擇。其餘不追問
- `just-do-it-spec.md`／`{slug}-spec-sa.md` 是使用者呼叫本指令的目的，直接寫入；三個知識資產檔案首次建立則必先徵求同意
